## 1. Общая идея проекта

Проект посвящён построению пользовательских эмбеддингов по последовательностям игровых событий.

Центральная идея:

- у каждого пользователя есть история действий в игре;
- эта история не просто набор событий, а именно последовательность;
- порядок событий может содержать поведенческий сигнал;
- хочется обучить модель, которая этот сигнал сожмёт в вектор пользователя;
- затем проверить, полезен ли этот вектор в downstream-задаче, например в прогнозе удержания.

У нас в итоге получилось две разные, но связанные задачи:

1. **Sequence task**  
   Насколько хорошо модель умеет предсказывать следующее событие по предыдущим.

2. **Downstream task**  
   Насколько полезны полученные представления пользователя в прикладной задаче retention.

Это разделение принципиально важно.

Почему:

- модель может отлично решать sequence-задачу;
- но это не гарантирует, что её embeddings будут лучшими для downstream;
- и именно это мы потом увидели на практике.

## 2. Почему структура проекта именно такая

Структура проекта:

```text
hse_recsys_rnn/
  src/
    __init__.py
    data.py
    splits.py
    baselines.py
    models.py
    train.py
    eval.py
    export.py
  notebooks/
    01_data_and_preprocessing.ipynb
    02_rnn_baseline.ipynb
    03_downstream_evaluation.ipynb
  artifacts/
    data/
    rnn/
    downstream/
  reports/
```

Это разделение было выбрано специально.

### 2.1. Почему не делать всё в одном ноутбуке

Если весь проект держать в одном ноутбуке, возникают типичные проблемы:

- код размазан по ячейкам;
- трудно понять, какая ячейка на что влияет;
- легко получить неявные зависимости на порядок запуска;
- трудно переносить логику между экспериментами;
- итог выглядит хуже и для защиты, и для сопровождения.

### 2.2. Почему не делать всё только в `.py`

Если сделать всё только в `.py`, теряется удобная исследовательская оболочка:

- таблицы;
- графики;
- комментарии по экспериментам;
- быстрые проверки гипотез.

### 2.3. Почему текущая схема хороша

Текущая схема делит обязанности:

- `src/` хранит **настоящую логику**;
- `notebooks/` показывают **исследовательский сценарий**;
- `artifacts/` хранят **результаты вычислительных этапов**.

Это позволяет:

- повторно использовать код;
- держать ноутбуки тонкими;
- не копировать одни и те же функции;
- аккуратно строить курсовую по этапам.

## 4. `src/data.py`: слой данных

Файл [data.py](../src/data.py) отвечает за всё, что происходит **до модели**.

Именно здесь сырые логи превращаются в последовательности пользователей.

### 4.1. Константы очистки

В начале файла зафиксированы три группы исключений:

- `TECH_EVENTS`
- `EXCLUDED_EVENTS`
- `EXCLUDED_PREFIXES`

Их смысл:

#### `TECH_EVENTS`

Это явно технические события:

- `BOOT_TIME`
- `BOOT_TIME_SECONDS`
- `AB failed to initialize`
- `SystemInitialized`
- `SystemInitializing`
- `Game loaded`

Они нужны приложению или логгеру, но не отражают поведение игрока как таковое.

#### `EXCLUDED_EVENTS`

Это служебные или агрегатные события:

- `PlayTimeMinutes`
- `PlayTimeAfkMinutes`
- `AB`
- `CohortData`
- `GameData`
- `Replay`
- `DebugAdEvents`

Здесь логика была такой:

- событие может формально быть “не техническим”;
- но при этом не нести полезного поведенческого сигнала для sequence-модели;
- или вводить шум.

#### `EXCLUDED_PREFIXES`

Префиксы:

- `__`
- `debug_`
- `test_`
- `internal_`

Они позволяют отфильтровать целые семейства служебных событий без перечисления каждого названия отдельно.

### 4.2. `PreparedSequences`

```python
@dataclass
class PreparedSequences:
    user_ids: list[str]
    user_sequences: list[list[int]]
    event2idx: dict[str, int]
```

Это главный контейнер после preprocessing.

Что в нём лежит:

- список пользователей;
- список их последовательностей уже в индексном виде;
- словарь `event_name -> index`.

Почему это важно:

- это уже почти готовый вход для модели;
- именно этот объект потом кочует в `02` и `03`.

### 4.3. `NextEventExample`

```python
@dataclass(frozen=True)
class NextEventExample:
    prefix: list[int]
    target: int
```

Это минимальная единица sequence-задачи.

Смысл:

- `prefix` — история событий;
- `target` — следующее событие.

Именно в такой постановке решается задача `next-event prediction`.

### 4.4. `EventWindowDataset`

Это одна из ключевых частей `data.py`.

```python
class EventWindowDataset(Dataset):
```

Он нужен для того, чтобы разрезать длинные пользовательские истории на окна.

#### Что он делает

Для каждой последовательности:

1. проверяет, что в ней есть хотя бы 2 токена;
2. выбирает стартовые точки окон через `stride`;
3. добавляет ещё `last_start`, чтобы последний кусок истории точно не потерялся;
4. вырезает окна длины `max_len + 1`;
5. сохраняет только окна длины хотя бы 2.

#### Почему `max_len + 1`

Потому что одно окно должно содержать:

- входную часть;
- и целевой следующий токен.

Если `max_len = 128`, то окно хранит `129` токенов:

- первые `128` идут в модель как вход;
- `129`-й токен нужен как target для последнего шага.

#### Почему нужен `stride`

Если брать только одно окно с начала или только одно окно с конца, мы теряем слишком много информации.

`stride` позволяет:

- нарезать длинные истории на несколько примеров;
- увеличить число train-сэмплов;
- лучше покрыть длинные пользовательские траектории.

#### `__getitem__`

На выходе возвращаются:

- `padded` последовательность;
- `length`.

Padding делается нулями до общей длины окна.

Это важно, потому что:

- в одном батче все последовательности должны иметь одинаковую длину;
- `0` у нас зарезервирован под `padding_idx`.

## 5. Потоковый preprocessing: почему именно так

Полный датасет оказался очень большим, поэтому логика “просто прочитать CSV целиком” была рискованной.

Из этого выросла функция:

```python
preprocess_event_logs_to_parquet(...)
```

### 5.1. Почему не хранить очищенный CSV

Мы осознанно выбрали `parquet`, а не `csv`, потому что:

- `parquet` компактнее;
- быстрее читается;
- хранит типы;
- лучше работает как промежуточный формат пайплайна.

### 5.2. `_normalize_event_chunk`

Это внутренняя функция, которая применяет все базовые правила очистки к одному чанку.

Что она делает:

1. добавляет `row_id`;
2. удаляет строки без пользователя, события или времени;
3. приводит типы;
4. удаляет строки с невалидным timestamp;
5. фильтрует мусорные события;
6. сортирует по:
   - `user_col`
   - `timestamp_col`
   - `row_id`

`row_id` нужен как устойчивый tie-breaker, если несколько событий имеют одинаковое время.

### 5.3. `preprocess_event_logs_to_parquet`

Это основной потоковый preprocessing.

Логика:

1. читается исходный CSV чанками через `pandas.read_csv(..., chunksize=...)`;
2. каждый чанк преобразуется в `polars.DataFrame`;
3. к нему применяется `_normalize_event_chunk`;
4. очищенный чанк пишется в:

```text
artifacts/data/clean_events/part_0000.parquet
artifacts/data/clean_events/part_0001.parquet
...
```

5. отдельно пишется `clean_events_summary.csv`.

### 5.4. Почему это хорошее решение

Потому что оно:

- одинаково работает и на sample, и на full data;
- не требует держать 18ГБ CSV в памяти;
- не плодит разные логики для разных размеров данных.

## 6. Загрузка очищенных данных

### 6.1. `load_clean_event_logs`

После chunked preprocessing мы читаем все `parquet`-части и объединяем их:

```python
df = pl.concat([...], how="vertical_relaxed")
```

Потом выполняется глобальная сортировка:

- по пользователю;
- по времени;
- по `row_id`.

Это важно.

Почему:

- локальная сортировка внутри чанка недостаточна;
- пользовательские события могут оказаться в разных чанках;
- нужна итоговая глобальная временная последовательность.

### 6.2. `load_event_logs`

Эта функция осталась для маленьких файлов.

Она читает CSV целиком и прогоняет тот же `_normalize_event_chunk`.

То есть:

- для sample можно читать напрямую;
- для full data правильнее сначала сделать `parquet`-части.

## 8. Построение словаря и последовательностей

### 8.1. `build_event_vocabulary`

Берёт уникальные `event_name`, сортирует их и строит отображение:

```python
event_name -> idx
```

При этом индексы начинаются с `1`, а `0` остаётся под padding.

Почему `0` нельзя давать реальному событию:

- `0` — специальный токен пустоты;
- embedding-слой использует `padding_idx=0`;
- loss и метрики умеют игнорировать этот индекс.

### 8.2. `build_user_sequences`

Это центральная функция слоя данных.

Что она делает:

1. заменяет `event_name` на `event_idx`;
2. группирует события по пользователям;
3. собирает каждую пользовательскую историю как список индексов;
4. удаляет слишком короткие истории:

```python
min_events_per_user = 10
```

Результат — объект `PreparedSequences`.

### 8.3. Почему порог `min_events_per_user = 10`

Это не абсолютная истина, а разумный стартовый порог.

Логика была такой:

- очень короткие истории плохо подходят для `next-event prediction`;
- у них почти нет контекста;
- они добавляют шум и уменьшают устойчивость эксперимента.

## 10. `src/splits.py`: фиксированный split по пользователям

Файл [splits.py](../src/splits.py) отвечает за единый split.

Это критически важно методически.

### 10.1. Почему split должен быть по пользователям

Если делить по событиям, а не по пользователям, то:

- куски истории одного и того же пользователя попадут и в train, и в test;
- возникнет утечка;
- качество будет искусственно завышено.

Поэтому split делается только по `user_id`.

### 10.2. `UserSplit`

```python
@dataclass
class UserSplit:
    train_user_ids
    val_user_ids
    test_user_ids
    seed
    val_ratio
    test_ratio
```

Это просто контейнер разбиения.

### 10.3. `build_user_split`

Делает двухшаговый `train_test_split`:

1. сначала выделяет `train` и временный хвост;
2. потом временный хвост делит на `val` и `test`.

Почему так:

- именно такую логику уже использовал Алексей;
- это делает твой split идейно совместимым с групповой работой.

Параметры:

- `train / val / test = 70 / 15 / 15`
- `seed = 42`

### 10.4. `save_user_split`

Пишет split в `split.json`.

### 10.5. `save_user_split_tables`

Дополнительно сохраняет:

- `split.json`
- `split_summary.csv`
- `split_users.parquet`

`split_users.parquet` очень полезен:

- одна строка = один пользователь;
- виден его split (`train`, `val`, `test`).

### 10.6. `apply_user_split`

Разбивает `PreparedSequences` на:

- `train`
- `val`
- `test`

То есть это уже мостик от preprocessing к обучению.

### 10.7. `describe_user_split`

Даёт summary по split:

- число пользователей;
- средняя длина последовательности;
- медиана;
- максимум.

Это позволяет проверить, не перекошены ли split’ы по длинам историй.

## 11. `src/models.py`: sequence-модели

Файл [models.py](../src/models.py) описывает рекуррентные модели.

### 11.1. `RecurrentEncoder`

Это общий базовый класс для:

- `GRU`
- `LSTM`

Он параметризуется через `rnn_type`.

### 11.2. Из чего состоит модель

#### 1. `nn.Embedding`

```python
self.embedding = nn.Embedding(vocab_size + 1, event_dim, padding_idx=0)
```

Смысл:

- каждый event index превращается в вектор длины `event_dim`;
- `padding_idx=0` гарантирует, что padding-токен корректно обрабатывается.

#### 2. Собственно `GRU` или `LSTM`

В зависимости от `rnn_type`.

#### 3. `projection`

```python
self.projection = nn.Linear(hidden_dim, vocab_size + 1)
```

Смысл:

- на каждом временном шаге скрытое состояние переводится в логиты по словарю;
- это и даёт возможность предсказывать следующее событие.

### 11.3. `forward`

Что делает:

1. эмбеддит вход;
2. пакует последовательности через `pack_padded_sequence`;
3. прогоняет через `GRU` или `LSTM`;
4. распаковывает обратно;
5. применяет линейную проекцию в пространство токенов.

Почему нужен `pack_padded_sequence`:

- в батче последовательности разной длины;
- padding не должен искажать реальные состояния;
- pack/pad позволяет RNN не тратить вычисления на хвостовые нули.

### 11.4. `encode`

Отдельный метод для извлечения user embeddings.

Он:

1. эмбеддит вход;
2. пакует последовательность;
3. берёт финальное скрытое состояние;
4. для `LSTM` извлекает `hidden` из пары `(hidden, cell)`;
5. возвращает последнее скрытое состояние последнего слоя.

Именно этот вектор потом считается embedding пользователя.

### 11.5. `GRUEncoder` и `LSTMEncoder`

Это тонкие классы-обёртки над `RecurrentEncoder`, чтобы код был читаемее.

`RNNEncoder = GRUEncoder` оставлен для обратной совместимости со старым кодом.

## 12. `src/train.py`: обучение

Файл [train.py](../src/train.py) отвечает за train-loop.

### 12.1. `choose_device`

Порядок выбора:

1. `cuda`
2. `mps`
3. `cpu`

Для твоего Mac это означало, что обучение реально шло на `mps`.

### 12.2. `seed_everything`

Фиксирует:

- `random.seed`
- `torch.manual_seed`
- `torch.cuda.manual_seed_all`

Это сделано ради воспроизводимости.

### 12.3. `train_model`

Это основной train-loop.

#### Критерий

```python
nn.CrossEntropyLoss(ignore_index=0)
```

Почему `ignore_index=0`:

- `0` — padding;
- нельзя считать loss по искусственным пустым токенам.

#### Оптимизатор

```python
AdamW
```

Это хороший и стандартный стартовый выбор.

#### Что происходит в одном батче

Из окна длины `max_len + 1` строятся:

- `inputs = batch[:, :-1]`
- `targets = batch[:, 1:]`

То есть задача формулируется как предсказание каждого следующего токена.

#### Почему `input_lengths = lengths - 1`

Потому что:

- исходное окно включает target-хвост;
- во вход модели идёт только последовательность без последнего токена.

#### Зачем gradient clipping

```python
clip_grad_norm_(..., max_norm=1.0)
```

RNN могут быть чувствительны к градиентам.  
Clipping добавляет устойчивость.

#### Что хранится в истории

Сохраняется средний token-level loss по эпохе.

Это потом использовалось для графика обучения.

## 13. `src/eval.py`: метрики

Файл [eval.py](../src/eval.py) отвечает за evaluation sequence-моделей.

### 13.1. `ranking_metrics_from_logits`

Эта функция принимает:

- `logits` формы `[num_examples, vocab_size]`
- `targets` формы `[num_examples]`

и считает:

- `MRR`
- `hit@k`
- `recall@k`

#### Как считается ранг

Идея:

- берётся score настоящего токена;
- считается, сколько логитов строго больше него;
- `rank = count_greater + 1`

Отсюда:

- `MRR = 1 / rank`
- `Hit@k = 1`, если `rank <= k`

### 13.2. Почему `recall@k` совпадает с `hit@k`

Потому что здесь на каждый пример ровно **один** правильный следующий токен.

В такой постановке:

- `recall@k`
- и `hit@k`

численно совпадают.

### 13.3. `evaluate_next_event_model`

Это evaluation loop для sequence-модели.

Он:

1. прогоняет батчи без градиентов;
2. считает loss;
3. разворачивает всё в плоский список next-token примеров;
4. агрегирует `MRR`, `Hit@k`, `Recall@k`.

На выходе даёт словарь:

- `loss`
- `mrr`
- `hit@1`, `hit@5`, `hit@10`
- `recall@1`, ...

## 14. `src/baselines.py`: простые baseline-модели

Это важный файл, потому что baseline’ы должны быть не декоративными, а нормальными.

### 14.1. `MostPopularBaseline`

Самая простая идея:

- посчитать глобальные частоты всех токенов;
- всегда предсказывать одни и те же глобальные популярности.

#### `fit`

Считает, сколько раз каждый токен встретился в train-историях.

#### `predict_scores`

Для любого числа префиксов возвращает одну и ту же строку score’ов.

### 14.2. `Markov1Baseline`

Это уже честный последовательностный baseline.

Идея:

- считаем матрицу переходов `prev -> next`;
- для текущего последнего токена смотрим его строку переходов.

#### `fit`

Строит:

- `transition_scores`
- `global_scores`

`global_scores` нужны как fallback.

#### `predict_scores`

Для каждого префикса:

- берётся последний токен;
- если по нему есть наблюдавшиеся переходы, используем их;
- если нет, откатываемся к глобальным частотам.

Это разумный baseline для next-event prediction.

### 14.3. `evaluate_baseline`

Гоняет baseline по списку `NextEventExample` и считает те же ranking metrics, что и для нейросетей.

Это делает сравнение честным:

- одна и та же постановка;
- одни и те же метрики.

## 18. Ноутбук `02`: sequence baseline

Файл:

- [02_rnn_baseline.ipynb](../notebooks/02_rnn_baseline.ipynb)

### 18.1. Его роль

Это блок про вопрос:

**насколько хорошо RNN кодирует последовательность событий?**

### 18.2. Что там происходит

1. загружаются `PreparedSequences` и split;
2. строятся sequence-примеры;
3. обучаются:
   - `GRU`
   - `LSTM`
4. считаются baseline’ы:
   - `MostPopular`
   - `Markov1`
5. сравниваются sequence-метрики;
6. строятся и сохраняются user embeddings.

### 18.3. Почему гиперпараметры были именно такими

Стартовая конфигурация:

- `max_len = 128`
- `stride = 64`
- `event_dim = 64`
- `hidden_dim = 128`
- `num_layers = 1`
- `dropout = 0.0`
- `batch_size = 128`
- `epochs = 5`
- `lr = 1e-3`

Логика:

- нужен не супертюнинг, а сильный и чистый baseline;
- медианная длина истории была около `83`, поэтому `128` — разумный старт;
- одна эпоха — это полный проход по всем training windows.

### 18.4. Итог sequence-результатов

На `test`:

- `MostPopular`: `MRR ~ 0.459`
- `Markov1`: `MRR ~ 0.813`
- `GRU`: `MRR ~ 0.880`
- `LSTM`: `MRR ~ 0.881`

Смысл:

- RNN-модели уверенно сильнее простых sequence baseline’ов;
- `LSTM` лишь минимально лучше `GRU`.

Это важный результат:

- sequence quality у RNN высокая;
- но `LSTM` не дала резкого скачка по сравнению с `GRU`.

## 19. Ноутбук `03`: downstream evaluation

Файл:

- [03_downstream_evaluation.ipynb](../notebooks/03_downstream_evaluation.ipynb)

### 19.1. Его роль

Это уже не про “умеет ли модель угадывать следующее событие”, а про:

**полезны ли embeddings в прикладной задаче retention?**

### 19.2. Главный методический риск: leakage

Самая важная проблема downstream-оценки:

если embedding строится по полной истории пользователя, а label зависит от будущего поведения, возникает утечка.

Именно поэтому в `03` была сделана **prefix-based** постановка.

### 19.3. Prefix-based логика

Для каждого пользователя:

- берётся только ранний префикс истории;
- по нему считаются:
  - baseline features;
  - GRU / LSTM embeddings;
- label строится относительно `prefix_end_ts`.

Так удалось избежать утечки по времени.

### 19.4. Почему исследовали `PREFIX_LEN = 50 / 100 / 150`

Это была осмысленная абляция.

Гипотеза:

- может быть, embeddings слабы не потому, что RNN плоха;
- а потому, что модели не хватает раннего контекста.

Поэтому мы проверили:

- `50`
- `100`
- `150`

### 19.5. Baseline features

Это был не “нулевой baseline”, а достаточно сильный user-level baseline.

Он включал:

- длину префикса;
- число уникальных событий;
- repeat ratio;
- число сессий в префиксе;
- число активных дней;
- доли top-k событий.

Именно поэтому downstream baseline оказался очень сильным.

### 19.6. Почему модель downstream — `XGBoost`

Потому что для tabular / mixed features это хороший, стабильный и объяснимый выбор.

Нам хотелось сравнивать именно **feature sets**, а не бороться между разными классификаторами.

### 19.7. Что сравнивалось

Для лучшего префикса сравнивались:

- `Baseline`
- `GRU`
- `LSTM`
- `Baseline + GRU`
- `Baseline + LSTM`

### 19.8. Итоги downstream

Главный вывод:

- увеличение длины префикса помогает;
- но чистые RNN-эмбеддинги не обгоняют сильный tabular baseline;
- `LSTM` не даёт устойчивого преимущества над `GRU`.

Это очень важный исследовательский результат.

Потому что он говорит:

- sequence quality и downstream usefulness — не одно и то же;
- сильная модель на `next-event prediction` не обязана стать лучшей в retention;
- главный фактор улучшения оказался не в усложнении RNN-ячейки, а в длине наблюдаемого раннего префикса.

## 21. Почему результаты выглядят именно так

Это важный концептуальный раздел.

### 21.1. Почему GRU/LSTM сильны на sequence-задаче

Потому что:

- next-event prediction действительно зависит от локального порядка событий;
- Markov1 уже сильный baseline, но RNN может хранить более длинный контекст;
- поэтому `MRR` заметно выше, чем у `MostPopular` и `Markov1`.

### 21.2. Почему downstream baseline оказался таким сильным

Потому что retention часто хорошо объясняется грубыми поведенческими признаками:

- сколько пользователь вообще был активен;
- сколько у него сессий;
- насколько разнообразно поведение;
- какова структура раннего префикса.

Для retention это бывает очень информативно.

### 21.3. Почему `LSTM` не дала большого выигрыша

Возможные причины:

1. задача уже достаточно хорошо решалась `GRU`;
2. разница между `GRU` и `LSTM` для этой постановки невелика;
3. downstream ограничивался не выбором ячейки, а качеством самого representation для retention.

### 21.4. Почему этот результат не является провалом

Это нормальный исследовательский вывод:

- одна модель сильна в sequence-постановке;
- но downstream определяется и другими факторами;
- простые признаки могут оказаться очень конкурентными.

Для курсовой это даже хорошо, потому что результат получился не декоративным, а содержательным.

### 23.1. “Почему RNN, а не сразу трансформер?”

Потому что:

- особенно `Markov1` — уже не игрушка, а честная последовательностная модель первого порядка.

### 23.3. “Почему embeddings не обогнали tabular baseline?”

Потому что:

- retention хорошо объясняется простыми агрегатными признаками;
- sequence representation училась на другой objective;
- strong sequence quality не гарантирует strongest downstream.

### 23.4. “Почему `LSTM` не помогла?”

Потому что:

- в этой постановке выбор `GRU` vs `LSTM` оказался вторичным;
- куда важнее было количество доступного раннего контекста.

### 23.5. “Что было самым важным улучшением?”

Для downstream — рост `PREFIX_LEN`.

Это и есть главный эмпирический вывод ветки RNN.
